# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Overview

BS42.NET is a multi-tenant e-commerce platform in a pnpm + Turborepo monorepo (started from the shadcn/ui Next.js monorepo template).

- `apps/console`: the admin dashboard (console.bs42.net, port 3000 in dev). Almost all current work is here.
- `apps/store`: the customer storefront (bs42.net). Browsing (with a featured-category carousel on the homepage), the basket, checkout with Paystack, sign-in, the account pages (orders, quotations, wish list, reviews, addresses, email preferences, trade account), product reviews, comparing products, installation, trade accounts, printable invoices, quotations and the Terms/Privacy pages are built (see Storefront and Orders and money). Its `start` script runs it on port 3001, next to the console on 3000 (`pnpm start` runs both after a build); `STORE_AUTH_URL` defaults to localhost:3001 in dev.
- `packages/*`: shared workspace packages imported as `@workspace/<name>` (the database package is `@workspace/db`). `@workspace/commerce` holds the order logic both apps use (see Orders and money).

## Commands

Run from the repo root (Turbo fans out to every package):

```bash
pnpm dev          # runs db:generate first, then next dev for both apps
pnpm build
pnpm start        # both built apps: the console on 3000, the store on 3001
pnpm lint
pnpm typecheck
pnpm format       # prettier --write
```

Lint uses the shared flat configs in `packages/eslint-config` (`base`, `react-internal`, `next-js`) with typescript-eslint. `eslint-plugin-only-warn` turns every rule into a warning, so `pnpm lint` exits 0 even with findings; read the output.

`pnpm-workspace.yaml`'s `overrides` pin patched versions of packages that other packages bring in, each limited to its vulnerable range (zod 4, fast-uri, mysql2), from the 2026-10-25 security review. Drop one once its parent depends on a fixed version (`pnpm why <package>`); `pnpm audit --prod` shows what's left.

Scope to one package with `--filter`, e.g. `pnpm --filter console dev`, `pnpm --filter @workspace/db db:migrate`.

Database (`packages/database`, reads `DATABASE_URL` from `packages/database/.env`):

```bash
pnpm --filter @workspace/db db:generate   # prisma generate -> packages/database/generated/prisma
pnpm --filter @workspace/db db:migrate    # prisma migrate dev
pnpm --filter @workspace/db db:deploy     # prisma migrate deploy
pnpm --filter @workspace/db db:seed       # the catalogue: categories, brands and the old site's products (prisma/seed.ts + seed-products.json, via tsx); skips existing ones
pnpm --filter @workspace/db db:seed:demo  # the same, plus a demo store with listings and today's rate if none (dev only)
pnpm --filter @workspace/db db:backfill-rates [days]  # past days' USD→GHS rates from Open Exchange Rates (default 90), only days with none
```

The seed's products are the old bs42.net catalogue: `prisma/seed-products.json` (276 products, generated, don't edit by hand) is built by `scripts/build-seed-data.mts` in the `bs42-legacy-products` folder beside this repo (the old site's export, with the migration's decisions in its `variant-groups.json` and a README), which also uploaded their images and documents to the storage container. So the seed's file URLs only work against that container, and a seeded product deleted in the console takes its files with it. Catalogue variants have no price, so each variant's old price is kept in the file and only the demo store's listing variants use it.

Better Auth owns most of the schema. After changing auth plugins or `additionalFields`, regenerate the Prisma schema with `pnpm --filter @workspace/auth auth:generate` (writes `packages/database/prisma/schema.prisma`), then create a migration. The script runs the CLI with `--conditions=react-server` (so `server-only` imports load) and `--env-file=../database/.env` (the plugins import the database client). It keeps the non-auth models; its only side effect is a blank line after top-level comments.

Tests use the built-in Node test runner and exist only in `packages/email` (`packages/utils` has a `test` script but no `tests/` directory yet):

```bash
pnpm --filter @workspace/email test                          # builds, then runs tests/*.test.mjs
cd packages/email && pnpm build && node --test tests/formatters.test.mjs   # single file
```

`@workspace/email` and `@workspace/storage` export from `dist/` (gitignored), so they must be built (`pnpm --filter @workspace/email --filter @workspace/storage build`) before the apps can import them. `turbo dev` does not build them for you.

## Architecture

### Two Better Auth instances, one database
`packages/auth` defines separate Better Auth servers that share `sharedAuthOptions` (Prisma adapter, cookie cache, user `additionalFields`, cross-subdomain cookies via `AUTH_COOKIE_DOMAIN`):
- `@workspace/auth/console`: `consoleAuth`. Sign-up is disabled; users arrive via invitations or the set-password email flow. Uses the `admin` + `organization` plugins from `console-plugins.ts`.
- `@workspace/auth/console-bootstrap`: a permissive instance used only by the first-run `/setup` action to create the initial superAdmin and the platform organization.
- `@workspace/auth/store`: storefront auth (email + Google, Google only when `GOOGLE_CLIENT_ID`/`_SECRET` are set; `isGoogleSignInEnabled`). Email sign-ups must verify their address before signing in; it refuses banned users itself (see Storefront).
- `schema-config.ts` exists only for `auth:generate`.

### Stores are organizations
A "store" is a Better Auth organization. One special organization, slug `PLATFORM_ORGANIZATION_SLUG` (from `@workspace/contracts`), represents the platform itself: it can't be deleted, has a fixed slug, and can't receive invitations. When a new store is created, `afterCreateOrganization` adds all system admins as members (superAdmin → `owner`, admin → `admin`).
- A store has a name, logo and status, and no shipping or returns policy of its own: customers never see stores, so delivery and returns are the platform's (Settings, Terms).
- Those memberships are the system's to keep: `beforeRemoveMember` / `beforeUpdateMemberRole` hooks refuse changes to a system admin's membership through Better Auth (`PLATFORM_STAFF`), since store owners can call its endpoints directly. The console's own flows (store creation, promote/demote) write through Prisma.
- Store member lists (`lib/data/members.data.ts`) leave platform staff out, and inviting one is refused (`PLATFORM_STAFF`). Member loaders select only the user fields the pages show: any member can see them.

### Two permission layers
- System roles (`user`, `admin`, `superAdmin`) on `User.role`, defined in `system-permissions.ts`. Role strings can be comma-separated; always check with `hasSystemRole` / `hasSystemPermission`, never `===`.
- Organization roles (`owner`, `admin`, `member`) on `Member.role`, defined in `organization-permissions.ts`. Besides Better Auth's defaults they have `listing` (owner/admin: create, update, delete; member: create, update) and `order` (owner/admin: read, create, update, refund; member: read, create). `refund` covers refunds and returns on the store's own orders. `purchaseOrder` (owner/admin: read, create, update, receive, cancel; member: read, receive) and `supplier` (owner/admin: create, update, delete).
- Trade accounts use the system permission `tradeAccount` (`read`, `update`; admins and superAdmins).
- The catalogue (brands, categories, products) is global, not per store: it uses the system permissions `brand`/`category`/`product` and `/catalogue` is admin-only in the global workspace. Platform orders use the system permission `order` (`read`, `create`, `update`; `refund` is superAdmin-only).
- **SuperAdmins**:
  - Only superAdmins can manage superAdmins: console actions check `canManageUserWithRole`, and a consoleAuth `hooks.before` blocks Better Auth's admin write endpoints.
  - User loaders in `lib/data/users.data.ts` hide superAdmins from everyone else.
  - The role is never set at creation. It changes only through `promoteToSuperAdminAction` / `demoteToAdminAction`, which update the role and every store membership (owner ↔ admin) in one transaction.

### Console access control
- **Workspace context**: the session's `activeOrganizationId` puts the console in either the "global" workspace (the platform org is active) or the "store" workspace (any other org).
  - The login form sets it (client-side `organization.setActive`, preferring the platform org). A session made anywhere else (signing in on the storefront, which shares the session cookie) starts with none; `proxy.ts` then picks the same one (`chooseWorkspace`), sets it through `setActiveOrganization` and redirects to the same page with the new session cookies (the console's session cache would otherwise say there's none for a minute), and `StoreSwitcher` does the same in a tab that was already open. A `?workspace=<id>` on any console URL (a store's or the platform's id, on every notification's link) switches to that workspace the same way, then drops the parameter. So don't use `changePassword`'s `revokeOtherSessions: true`, which replaces the current session: change the password, then call `revokeOtherSessions` (as `updatePasswordAction` does).
- **Route rules**: `apps/console/lib/route-access.ts` (`routeAccess`) is the single source of truth for which system roles and contexts may visit each path prefix.
  - `apps/console/proxy.ts` (Next's renamed middleware) enforces it.
  - The sidebar uses `checkAccess` to filter `lib/nav-config.ts`. In a store's workspace each store page is its own item (Orders, Listings, Product Requests, Purchase Orders, Transfers, Suppliers, Members, Invitations), with Store Details (`/store`) at the bottom; it's `exact`, so it isn't highlighted on the pages under it. The global workspace keeps Catalogue as a collapsible group (Products, Categories, Brands, Reviews, also the cards on `/catalogue`).
  - Every nav URL needs a matching entry (or parent prefix) in `routeAccess`.
  - Breadcrumbs (`AppHeader`) come from `BREADCRUMB_DATA` in `constants.ts`, one entry per page: a new page needs one. `[id]` in a pathname matches one segment, and a link may use it (filled in from the URL), so a page can link back to its record. A page without an entry shows its sidebar section.
  - Unlisted paths are allowed through, so they rely on page-level guards.
- **Page/action guards**: `apps/console/lib/auth-guard.ts` provides `requireConsoleAccess`, `requireConsoleAdmin`, `requireSystemPermission`, `requireOrganizationPermission` and `requireActiveStoreMember` for server components and actions, and `hasStorePermission` / `getStoreRole` for actions and loaders that must return an error rather than redirect.
  - Every page calls its own guard as its first statement; layouts do not guard (they aren't re-run on client navigation). A new page without a guard is open to any signed-in user, including storefront customers who share the auth cookie.
  - Global admin pages: `requireSystemPermission(...)` (or `requireConsoleAdmin()` when no permission exists yet). Pages for all console users (dashboard, `/account/*`): `requireConsoleAccess()`.
  - Store workspace pages: `requireActiveStoreMember()`, which returns `{ session, storeId, role }` for a membership of the active store (never the platform org; a user removed from it goes to `/`). A page that needs more checks `organizationRoles[role].authorize(...)` and redirects to `/forbidden`. Store actions take the store id from the page, not the session's active org (another tab may have switched it), and check `hasStorePermission(userId, storeId, ...)`.
  - The `user` system role has no permissions, so `requireSystemPermission` can't express "store staff"; use store membership for that.

### Database client extensions
`@workspace/db` exports a Prisma 7 client (driver adapter `@prisma/adapter-pg`, generated into `packages/database/generated/prisma`) wrapped in `$extends` query hooks:
- **Slugs** (organizations, brands, categories and products) are generated server-side from the name, with uniqueness retries. Any client-supplied slug is discarded, so callers send a placeholder (Better Auth requires one; Prisma's types require one for brands, categories and products). The exception is the platform org. Only a rename changes a slug, so moving a category keeps its URL; a taken category slug tries the parent's slug as a prefix (`men-accessories`) before numbering.
- **SKUs**: a simple product created without a SKU gets one (`IPHONE15-K3ZQ`). Variant SKUs come from `generateUniqueSku(tx, name)`, called by the action: a query hook can't read the transaction it runs in, so it couldn't see a product created earlier in it.
- **File cleanup**: deleting an organization, user, brand, category or product removes its files from Azure Blob Storage after the delete commits (`removeFiles` from `@workspace/storage`); for a product that's its images, banner, variant images and documents. Files nothing references any more, such as uploads from a form left without saving, are removed by `sweepOrphanedFiles` (`packages/database/src/file-sweep.ts`), which `POST /api/cron/file-cleanup` runs for a scheduler using `CRON_SECRET`. A new column holding file URLs must be added to both lists in `file-sweep.ts` (`getReferencedFileUrls` and `findReferencedFileUrls`), or the sweep deletes its files and the storage delete route stops protecting them.

`readAppSettings()` reads the singleton `AppSettings` row (falling back to `DEFAULT_APP_SETTINGS`). The console caches it via `unstable_cache` with the `app-settings` tag. Settings is split into pages (`/settings` General, `/settings/pricing`, `/settings/delivery`, `/settings/notifications`, `/settings/legal`; `settings/layout.tsx` with `SettingsNav`, styled like the storefront's account menu), each made of cards that save on their own: full-width fields, an icon-and-"Save" button at the bottom right, and grouped switch cards in a plain `div` with `gap-3` (a `FieldGroup` inside `SettingsCard`'s own is forced to `gap-4`). The `AppSettings` cards (`SettingsCard`, `settings-cards.tsx`) each save only their own fields through `saveSettingsSection(section, values, original)`, with a schema per section (`settingsSectionSchemas`) and the values the card loaded (`sectionValues` in `lib/settings-sections.ts`): it locks the row and refuses with `CONFLICT` when those fields changed since, so a card can't undo someone else's save but different cards never clash. The exchange rate, delivery fees, installation areas and legal pages are stored elsewhere and keep their own cards and actions.

Migrations: Prisma doesn't model `CHECK` constraints or triggers, so they live in the migration SQL (stock, quantities, ratings, tax rates, one value per spec value row, delivery fees; the category cycle trigger). `prisma migrate dev` is interactive when a change could lose data (e.g. removing an enum value), so in a non-interactive shell generate that migration with `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`.

### Categories
- A self-referencing tree (`parentId`, `onDelete: NoAction` on purpose: Postgres checks it at the end of the statement, so a `deleteMany` can remove a parent and its children together, which `Restrict` would reject).
- Names are unique among siblings (`@@unique([parentId, name])` plus a partial index for top-level names, via the `partialIndexes` preview feature). Siblings are ordered by `position`, then name.
- The `category_prevent_cycle` trigger rejects moving a category under itself or a descendant. Under the driver adapter its `category_no_cycle` error only appears in the error's `meta`; `updateCategoryAction` maps it to `PARENT_CYCLE`.
- `lib/data/categories.data.ts`: `getCategoryTree` (for `DataTableTree`), `getCategoryOptions(editingId?)` for the parent select (archived categories and the edited category's own subtree are disabled), `getCategoryById` (with `childCount`). Deleting a category with subcategories returns `HAS_CHILDREN`.
- **Specifications** (`CategorySpec`, with `CategorySpecOption` for choices and `ProductSpecValue` per product): what products can list, such as a camera's resolution, for the storefront's filters. A spec applies to its category and every category under it, so a product has its category's specs and those above it (top category first, then each category's by `position`). Types: `SELECT` (an option row, so renaming an option keeps products' values), `NUMBER` (optional `unit`), `BOOLEAN`, `TEXT`; a CHECK in the migration keeps exactly one value column set. A spec's type can't change (`TYPE_LOCKED`), and a name can't repeat along a branch, above or below (`NAME_EXISTS`). Managed in the Specifications card below the category's edit form (`lib/actions/category-spec.actions.ts`, each change saves on its own; edits send `updatedAt`, `CONFLICT`); values are optional and per product, not per variant (a spec a product varies by is a variant option). `lib/product-specs.ts` checks and saves them (`saveProductSpecs`, replacing the product's values in the product's transaction; `INVALID_SPEC`); values for specs that don't apply are dropped, so moving a product to another category clears them, and moving a category leaves its products' old inherited values unused until they're next saved.

### Products
- One form for add and edit (`catalogue/products/_components/product-form.tsx`). Products go in leaf categories only, and a published product needs a sell price above 0. Its Specifications card follows the category field, from every category's specs loaded with the page (`getSpecFieldsByCategory`); the form holds values by spec id (`specs`: an option id, `"true"`/`"false"`, text or a number, with `""` or `SPEC_NOT_SET` for none).
- The products list (`getProductsForTable`) reads the category tree once per page for each row's path ("Men / Shoes") and for the category filter, which includes subcategories. Search (`search`) matches the name, SKU and barcode, including variants'. The category filter is a tree (the `tree` filter type), and each row notes what it's missing of pictures, a description and a sell price, with a Details filter (`incomplete`, `PRODUCT_DETAILS`; a product written without pictures, as the old sample seed did, holds NULL, which `isEmpty` doesn't match).
- Ticking products offers "Set status" and "Move to category" (`setProductsStatusAction`, `moveProductsAction`, system permission `product: update`, all or none). Publishing refuses with `NO_PRICE`, naming the products without a sell price; moving needs a leaf category and clears values for specs the new category doesn't have, as the form does.
- `updateProductAction` updates options, values, variants and documents in place, matched by id (`lib/product-sync.ts`). Store listing variants hang off variants and cascade, so recreating a variant would wipe the stores' prices and stock for it. A removed variant that has been ordered, directly or through a store's listing, or bought in on a store's purchase order, is archived instead of deleted.
- Store staff see a product read-only at `/store/products/[id]` (`getStoreProductDetails`, any store member: published products, or any their store lists), linked from the listings table and the listing form, with "Edit listing" or "List in this store", and "Edit in catalogue" for system admins.
- The edit page has a Storefront card (`StorefrontLinkCard`, `lib/data/storefront-links.data.ts`): "View on storefront" while some store's listing is visible to customers, else why not; the listing edit page has the same for its listing (`hiddenReason`).
- The edit loader (`getProductForEdit`) sends plain values plus `savedFiles` (the form never deletes those; the action removes replaced ones after it commits) and each variant's usage, so the form can warn before removing a listed or ordered variant.

### Product requests
- A store asks for a product the catalogue doesn't have (`ProductRequest`, `/store/product-requests`, its own sidebar item; "Request it" on the Add Listing picker): a name, and optionally a brand (existing, or a typed name with "Not in this list"), a category (any level), a barcode or part number, a link and notes. Any store role with `listing: create` (all of them) can ask and cancel while it's pending. As they type, the form lists published products matching the barcode/SKU or every word of the name (`findCatalogueMatches`), each with "List it".
- Platform admins answer at `/catalogue/product-requests` (pending first, oldest first; also a `/catalogue` card and a dashboard "Needs attention" row) and each request's page: "Add the product" opens Add Product with `?request=` (`getProductRequestForProductForm` fills in the name, brand, category when products can go in it, and barcode; a card shows the rest), and `createProductAction(input, requestId)` marks it `CREATED` in the product's transaction while it's still pending; "Already in the catalogue" links a product (`MATCHED`); "Decline" needs a reason the store sees (a CHECK in the migration). Each refuses `NOT_PENDING` when someone got there first.
- A new request goes to the platform (`notifyProductRequest`, the `PRODUCT_REQUESTS` alert, on by default); the outcome goes to whoever asked, by bell and email (`notifyProductRequestDecision`), linking to "List it" or their requests.

### Store listings
- A listing is a store's price and stock for a catalogue product, with a `StoreListingVariant` per variant on sale. A variant without its own sell price sells at the listing's.
- The listings table (`getStoreListings`) filters by stock (in / low / out / not tracked, worked out like the stock column's badges: a listing with variants counts its variants on sale against the listing's low-stock threshold, which saving a listing copies to its variants; that compares across tables, so the ids come from SQL), brand, category (with subcategories) and "visible to customers" (the storefront's rule, below; the table's "Not on sale" note gives the reason).
- **Visible to customers** (`@workspace/commerce/visibility`): the listing, its product and its brand published, its category and every category above it published, the store active, and a price above 0; with variants, at least one variant on sale (`variantOnSaleWhere`: published in the store, not archived in the catalogue) whose own price, or else the listing's, is above 0. It has two forms that must agree: `customerVisibleListingWhere(visibleCategoryIds)` for queries and `hiddenReason(listing, visibleCategoryIds, variantsOnSale?)` for loaded rows (the reason is for staff). Prisma can't follow the category tree, so `getVisibleCategoryIds` / `loadVisibleCategoryIds` work the visible ids out from the whole tree. Storefront orders (`resolveOrderLines` with no store) refuse anything hidden; staff orders in a store keep their own checks (listing, product and variant published), and refuse a suspended store (`STORE_SUSPENDED`, in `priceStoreOrder`; the create-order page explains it).
- **Stock history**: every change to a listing's or variant's stock writes a `StockMovement` (the change, the stock after, a reason, who, and a link to the order, return or purchase order delivery behind it) in the same transaction, so the movements add up to the current stock. Writers use `@workspace/commerce/stock-movements`: `addStock` (add-only, for cancellations, returns and deliveries; taking stock away needs a guard against going below 0, as a sale reserves it) or `recordStockMovement(s)` for a change already written. They cover a sale, a cancellation, a restocked return, a purchase order delivery, a stock transfer (sent, received or cancelled), a new listing's (or newly added variant's) initial stock, and an edit on the listing form, which must give a reason (`stockReason`: count correction, damaged, lost, or other with a note; `STOCK_REASON_REQUIRED`). Anything new that changes stock must do the same. The history is at `/store/listings/[id]/stock-history` (`lib/data/stock-history.data.ts`); reason labels are in `lib/stock-reasons.ts`.
- `updateListingAction` runs `lib/listing-sync.ts`. The edit form sends back the values it loaded (`original`); inside a transaction that locks the listing's rows (`SELECT … FOR UPDATE`), a change someone else made returns `CONFLICT`, and stock the user changed that changed meanwhile (a sale) returns `STOCK_CHANGED` with the current stock, which the form merges in. Stock the user left alone is never written.

### Orders and money
- Catalogue prices (products, store listings, variants) are USD. Customers are charged in GHS at the day's exchange rate (`ExchangeRate`, one row per pair per day, `rate` = units of `to` per 1 `from`). Order amounts are named after their currency (`subtotalUsd`, `subtotalGhs`, `shippingGhs`, `taxGhs`, `totalGhs`, `unitPriceUsd`/`unitPriceGhs`, ...).
- Each order line stores its GHS amounts, its share of the discount (`discountGhs`) and its tax (`taxGhs`), each rounded once; the order's subtotal, discount and tax are their sums, so receipts add up. `totalGhs = subtotalGhs - discountAmountGhs + shippingGhs + installationGhs + taxGhs`. Orders copy the exchange rate and tax rate they used.
- The platform is the seller of record: one tax rate in `AppSettings` (`taxEnabled`, `taxRate` as a fraction, `taxShipping`). Shown prices exclude tax; tax is charged after the discount. Do all money maths with `Prisma.Decimal`, never JS numbers (`AppSettingsData.taxRate` is a plain number only so it can reach client components).
- Anything that has been ordered is archived, never deleted: `OrderItem`'s links to stores, listings, variants and products are `Restrict`, and its snapshot fields keep what was sold at the time. Delete actions should return a code ("archive it instead") rather than hit the foreign key. Purchase order lines restrict the same way (see Purchase orders). `PaymentStatus` is the source of truth for money; `OrderStatus` tracks fulfilment only.
- **Exchange rate**: `POST /api/cron/exchange-rate` (a scheduler, daily after midnight Accra time, `Authorization: Bearer $CRON_SECRET`) saves today's USD→GHS rate from Open Exchange Rates (`OPEN_EXCHANGE_RATES_API_KEY`, `lib/exchange-rate-fetch.ts`). It only fills a day with no rate, and refuses a rate more than 20% from the previous one (answering 502, market rate against market rate). It saves the market rate (`ExchangeRate.marketRate`) and, as `rate`, that plus Settings' markup (`AppSettings.exchangeRateMarkupPercent`, 0-10%, 0 by default), to cover the cedi moving between pricing (or a quotation) and payment; a rate set by hand is used as typed. A superAdmin can set or override today's rate in Settings (`setTodaysExchangeRateAction`); `ExchangeRate.source` records which. Orders refuse a rate older than `EXCHANGE_RATE_MAX_AGE_DAYS` (2) with `NO_RATE`, and a day's rate can't change once an order has used it (`RATE_IN_USE`).
- **Shared with the storefront**: `packages/commerce` (`@workspace/commerce/<module>`, exported from source) holds what both apps need: `pricing` (pure; `shelfPrice` is the storefront's shown price), `order-status`, `exchange-rates` (`getLatestExchangeRate`, `getPricingContext`), `stock-movements`, `order-writes`, `order-emails`, `notifications`, `visibility`, `delivery` (with `delivery-rates`), `installation` (with `installation-areas`), `paystack`, `online-payments`, `order-links` (the signed order and quotation links, `orderHref` / `orderUrl` / `invoiceHref` / `invoiceUrl` / `isOrderKey`, `quoteHref` / `quoteUrl` / `isQuoteKey`), `trade-accounts` (with `trade-account-status`), `customer-orders` (`accountOrdersWhere`) and `reviews`. Only `order-status`, `delivery-rates`, `installation-areas` and `trade-account-status` are safe in client components: they import no values from Prisma's client. Staff-only order changes (`lib/order-updates.ts`, `lib/order-refunds.ts`) stay in the console and import from it. Its modules import each other relatively, so scripts can run them like the console's transaction modules.
- **Delivery fees** (Settings → Delivery, `DeliveryRate` + the `DeliverySettings` singleton): GHS, not USD, since couriers charge in cedis. A region's fee (`town` null) and town fees that override it, named as in `GEODATA`; an address with neither isn't delivered to, so a region with only town fees delivers only to them. Orders whose subtotal after the discount reaches `freeDeliveryFromGhs` deliver free; one fee per order, whatever its weight. `@workspace/commerce/delivery` quotes it (`quoteDelivery`, `loadDeliverySettings`); the lookup alone is in `delivery-rates` for client components. The Delivery card replaces every rate on save (`saveDeliverySettingsAction`, versioned by the singleton's `updatedAt`, kept apart from `AppSettings` so the two Settings forms don't conflict). The create-order wizard fills the shipping fee in from it when the area changes; staff can still change it, and apply free delivery themselves.
- **Installation** (storefront orders and orders the platform creates, never a store's own: the platform's installers do it, and a store's create-order wizard deliberately doesn't offer it): a GHS fee per unit, from the product (`Product.installation`: `CATEGORY`, the nearest category up the tree with an `installationFeeGhs`; `OWN`, its own `installationFeeGhs`; or `NONE`), resolved by `installationFee` / `loadInstallationFees` in `@workspace/commerce/installation`. Installers work in the areas in Settings → Delivery's Installation card (`InstallationArea`, a whole region or towns, replaced together and versioned by the `InstallationSettings` singleton's `updatedAt`); `installsIn` / `describeInstallationAreas` are in `installation-areas`. A basket line installs every unit or none (`CartItem.withInstallation`: the product page's checkbox, a switch per basket line; `loadCart` takes it off with a notice when the product stops offering it); checkout refuses an address outside the areas (`NO_INSTALLATION`) and the free-delivery threshold counts goods only. Each order line keeps `installationUnitGhs` (null: none), `installationTotalGhs` and `installationTaxGhs`, rounded once; the order's `installationGhs` is their sum, its `taxGhs` includes their tax, and the discount never applies to installation. The order has one installation status (`TO_ARRANGE` → `BOOKED` (rebookable, with `installationDate`) → `DONE`, or `CANCELLED`; `nextInstallationStatuses`, `installationBlockedReason`: paid and not cancelled), with `OrderInstallationHistory` for the timelines. The platform's order page has the Installation card (`components/orders/installation-card.tsx`; a store's page shows it read-only): booking emails the customer (`INSTALLATION_BOOKED`, `OrderInstallationBooked`), and "Cancel installation" (system permission `order: refund`) refunds what it cost in the same transaction (`lib/order-installation.ts`, `installationLeftGhs`: the units not brought back). Cancelling the order cancels it too. A return suggests refunding the returned units' installation while it's still to happen. Store dashboards count a store's own orders' totals with their installation, as with delivery.
- **Pricing**: `@workspace/commerce/pricing` (pure, `Decimal` only) implements the maths above. The discount is split by line totals, rounded down, with the remainder on the last line. Prices always come from published listings on the server (`resolveOrderLines`), never from the browser: given a store id, only that store's (staff orders); given null, any store's, each line keeping its own store (`ResolvedLine.storeId`, for the storefront).
- **Store orders** (`/store/orders`): a store manages only orders made entirely of its own items; an order spanning stores is the platform's (global `/orders`), and the store sees only its own lines.
  - `@workspace/commerce/order-writes` creates orders (`createOrder`, with `createdById` null and its own `statusNote` for a storefront order) and changes their status (`changeOrderStatus`; `changedById` null for an automatic change). Stock is reserved at creation with an atomic `updateMany({ stock: { gte } }, decrement)` per tracked row (`INSUFFICIENT_STOCK` rolls the whole order back) and restored when the order is cancelled. Each line records whether its sale took stock (`OrderItem.tracksStock`, the row's tracking at the time), and cancellations and restocking returns go by that, not by how the row tracks stock now.
  - Status changes follow `@workspace/commerce/order-status` (`nextOrderStatuses`: shipped is for delivery only, cancel until shipped with a reason, completed needs a recorded payment, `hasBeenPaid`) and apply only from the status the page showed (`STATUS_CHANGED`). Nobody cancels a paid order through a status change (`PAID_ORDER`): it needs a refund.
  - Payment is recorded separately ("Record payment", with `paymentRecordedById`), never as a side effect of a status.
  - References are `BS42-yyyyMMdd-00001` from the Postgres sequence `order_reference_seq`, created in its migration's SQL; gaps are expected.
- **Platform orders** (`/orders`, system permission `order`): every order from every store, with a Store column, the amount refunded under the Total, and filters (`lib/data/orders.data.ts`; the "more than one store" filter gets its ids from SQL).
  - **Creating one** (`/orders/create`, system permission `order: create`, "Create Order" on `/orders`): the staff quote wizard's steps (`components/staff-sales/*`, shared with `/quotes/create`; each step takes any form with `StaffSaleFields` and reads it through `asStaffSaleForm`) with items from any store at the storefront's offer, installation per line, delivery only (a recipient, the fee filled in from Settings), how the customer will pay (`STAFF_ORDER_PAYMENT_METHODS`: bank transfer, mobile money, cash) and internal notes. A looked-up trade account's discount is where the discount starts and its company and TIN go on the order; a discount needs `order: update`. `createStaffOrder` (`lib/staff-orders.ts`, pricing through `priceStaffSale` in `lib/staff-quotes.ts`) creates it unpaid with its stock reserved ("Created by the platform") at the total the review step showed (`PRICE_CHANGED` otherwise, and the review prices it again); staff record the payment, and the unpaid-order job leaves it. Email is optional, as on store orders, and editing a looked-up customer's email unlinks their account. A town outside the installation areas is `OUTSIDE_INSTALLATION_AREAS` (staff quotes too), unlike `OrderItemError`'s `NO_INSTALLATION` (a product that stopped offering it). Both wizards' review steps offer "Deliver free" once the goods after the discount reach the free-delivery threshold.
  - **Bank transfer**: Settings → Pricing's Bank Transfer card (`AppSettings.bankTransferDetails`, plain text as typed, up to 1,000 characters) is shown, with the order's reference to quote, while a staff-made order is unpaid by bank transfer (`awaitsBankTransfer` in `order-status`): on its confirmation email, its storefront page (which, for any staff-made order, asks for payment as arranged rather than online, and doesn't offer putting a cancelled one back in the basket) and its invoice.
  - The details page has the store page's controls. Both pages share `components/orders/*` (which take `storeId: string | null`, null on the platform's pages, and check permission with `useCanUpdateOrders`), `lib/order-details.ts` (loader mapping) and `lib/order-updates.ts` (status, payment and pending edits behind both sets of actions).
  - Customer emails (`@workspace/commerce/order-emails`) are scheduled with Next's `after()` once a create, status change or recorded payment has committed (created, confirmed, shipped, delivered, cancelled, payment received, refunded, returned; completed sends the "How was your order?" review request (`OrderReviewRequest`) for the products the customer hasn't reviewed, or nothing; processing sends none). They're skipped when the order has no `customerEmail` or the linked account has `getOrderEmails` off, and pickups get no shipped/delivered email.
- **Refunds and returns**: superAdmins on any order (`/orders`, system permission `order: refund`), and a store's owners and admins on orders made only of its items (store permission `order: refund`; an order shared with other stores is the platform's). Both sets of actions call `giveRefund` / `cancelWithRefund` / `recordReturn` in `lib/order-updates.ts`, with the transactions in `lib/order-refunds.ts`; the components take `storeId` and check with `useCanUpdateOrders(storeId, "refund")`. System admins are members of every store but refund by their system role there too (admins can't, superAdmins can; `checkRefundable`). A refund by a store's own staff also emails the platform's staff (`notifyRefund`, the `notifyStoreRefunds` switch, on by default); a superAdmin's doesn't. A refund on an order made only of one store's items, by anyone, emails that store's team (see Staff notifications).
  - Refunds (`OrderRefund`): any amount up to what's left, which sets `PARTIALLY_REFUNDED`/`REFUNDED`; money only, a refund never restocks. "Cancel and refund" refunds the rest and cancels in one transaction, until the order has shipped. Both lock the order row and take the refunded total the page showed (`REFUNDS_CHANGED`).
  - Returns (`OrderReturn` + `OrderReturnItem`, `recordOrderReturn`): once an order is delivered or completed (`canBeReturned`) and its payment recorded (so a later "Record payment" can't count returned items as paid; `returnBlockedReason` says why the button is missing), with no time limit. Per line, how many came back (never more than sold, counting earlier returns) and whether they go back into stock (only rows that track it). The optional refund is a linked `OrderRefund`; the form suggests what those units cost the customer (`returnedUnitsAmount`: the line after its discount, with its tax, on a running total so a line returned in parts adds up), never shipping. The order's status doesn't change; the lines show the returned counts, the header and `/orders` show "Returned"/"Partly returned" (`returnLabel`), and `/orders` filters by "Returns". A return's refund shows on the return's timeline entry, not as a separate refund. It also takes the number of returns the page showed (`RETURNS_CHANGED`) and sends one `RETURNED` customer email.

### Purchase orders
- A store buys stock in with purchase orders (`/store/purchase-orders`) from its own suppliers (`/store/suppliers`, `Supplier`, unique name per store; one on a purchase order is archived, never deleted). Owners and admins create, edit and cancel them; every store role can see them and receive deliveries (whoever unpacks the boxes). System admins do the same in any store through their store membership. The writes are in `lib/purchase-order-writes.ts` (tested against the database like the other transaction modules); `lib/purchase-order-status.ts` holds the rules both sides use.
- Statuses: `DRAFT` (changes nothing; can be deleted) → `ORDERED` → `PARTIALLY_RECEIVED` → `RECEIVED`, or `CANCELLED` (ordered, nothing arrived) / `CLOSED` (partly received, the rest isn't coming). What's left on ordered and partly received lines is **incoming** stock, worked out, never stored (`getIncomingStock` / `getIncomingByListing`), and shown on the listings table and the form's search. An open order whose `expectedOn` is before today (Accra) is **overdue** (`overduePurchaseOrderWhere`): a badge, the list's Delivery filter (`?overdue=true`) and a "Needs attention" row on both dashboards.
- What's on its way also counts transfers in transit to the store (see Stock transfers).
- Ticking listings on the listings table offers "Create purchase order" (`DataTable`'s `selectionActions`), which opens the create page with `?listings=` (`findPurchasableListings`, shared with the form's search). `suggestPurchaseLines` starts each row still at or under its low-stock threshold once incoming arrives at enough to reach twice the threshold; a listing with no such row gets each row at 1.
- The platform's read-only view (`/purchase-orders`, system admins, `requireConsoleAdmin`) lists every store's, with a Store column and filter; its details page is the store's (`components/purchase-orders/purchase-order-view.tsx`) with "Open in <store>" instead of the actions (`?workspace=` switches to the store, where system admins act as members). The loaders take `storeId: null` for it.
- Costs are kept in the order's currency as invoiced (`unitCost`, `shippingCost`); each line also keeps `unitCostUsd`. An order in GHS converts at the latest rate while it's a draft and takes the day's rate when it's marked as ordered (`exchangeRate`), which its lines keep from then on; no current rate refuses with `NO_RATE`. Shipping isn't spread over the lines.
- Receiving (`PurchaseOrderReceipt` + items) locks the order row, takes the number of deliveries the page showed (`RECEIPTS_CHANGED`), refuses more than is left (`TOO_MANY`), adds stock only to rows that track it, and can set each listing's (or variant's) `buyPrice` to the line's USD cost ("Update buy prices", on by default; needs `listing: update`).
- Edits take the order's `updatedAt` as a version (`CONFLICT`). Once ordered, the supplier and currency stay, and a line can't drop below what has arrived (`BELOW_RECEIVED`). Cancelling and closing take the status the page showed (`STATUS_CHANGED`).
- Purchase orders link to their store, and their lines to listings and variants, with `Restrict`, like order lines: a listing, variant or product that has been bought in is archived, never deleted (the `HAS_ORDERS` checks and `product-sync.ts` count them), and `beforeDeleteOrganization` refuses a store with purchase orders.

### Stock transfers
- A store sends stock to another store at `/store/transfers` (its own sidebar item; `StockTransfer` + `StockTransferItem`, `TR-yyyyMMdd-00001` from `stock_transfer_reference_seq`), only between stores the sender manages: owner or admin in both (`TRANSFER_ROLES`, `getTransferDestinations`), so one business's branches, and platform admins anywhere. Stock only: no prices or money.
- Sending (`createStockTransfer` in `lib/stock-transfer-writes.ts`, tested against the database like the other transaction modules) takes each line from the sender's row at once, guarded so it can't go below 0 (`INSUFFICIENT_STOCK` rolls it all back), as `TRANSFER_OUT`. The sender's rows must track stock (`NOT_TRACKED`) and the receiver must list each product and variant, not archived (`NOT_LISTED`, naming them).
- The receiving store (any role) receives it once (`receiveStockTransfer`), entering what arrived per line; that's added to its rows that track stock (`TRANSFER_IN`), and any shortfall was lost on the way (`quantityReceived` < `quantity`, no movement: it already left the sender). The sender's owners and admins can cancel it until then (`cancelStockTransfer`, `TRANSFER_CANCELLED`, the stock goes back). Both lock the transfer row and refuse `STATUS_CHANGED`.
- In transit counts as the receiver's incoming stock (`getIncomingStock` / `getIncomingByListing`), not the storefront's "Due" lines. Transfer lines restrict deleting either side's listings, variants and stores, like purchase order lines (the `HAS_ORDERS` checks, `product-sync.ts`, `beforeDeleteOrganization`).
- `notifyStockTransfer` tells the other side under each owner's and admin's per-store stock switch: the receiver when it's sent or cancelled, the sender when it's received (with any shortfall).

### Dashboard
`/` shows the active workspace's dashboard (`app/(root)/page.tsx`), laid out after shadcn's dashboard-01 block: a store's for a member of the active store, the platform's for system admins in the global workspace. Both have stat cards with the change from the previous period, a net-sales-per-day area chart (shadcn `chart`, Recharts) whose toggle sets the period for the whole page (`?period=7d|30d|90d`, default 30 days, whole days in Accra time), "Needs attention" rows linking to the matching filtered lists (only those with a count; "All caught up" when none), and the 10 latest orders in a table beside an order card (after the old dashboard-05 block) that sums one up, browsed with its previous and next buttons or by clicking a row. The table is a picker (reference, customer, status, total); the card holds the rest in accordion sections (order details open by default; each closed section's header shows its key fact), with the status badges in its header. The card is built from the details pages' mapping (`getRecentStoreOrderDetails` / `getRecentOrderDetails`), trimmed by `toOrderSummary` to what it shows; the platform's adds an exchange-rate chart beside the best sellers (`ExchangeRateChart`, the rate prices used per day of the period, with the market rate dashed when a markup makes them differ and a dot on days set by hand; `db:backfill-rates` fills in past days), per-store stock alerts (linking to each store's listings with `?workspace=`, a full page load: `AttentionItem.switchesWorkspace`) and checks (exchange rate, tax, mailer, notification recipients). Both count overdue purchase orders (the platform's also product requests waiting), and list the period's five best sellers (`TopSellers`, by revenue or units: lines on orders paid in the period and not cancelled, less units returned since; revenue is the goods after their discount, before tax), a store's per listing (its own lines, shared orders included) and the platform's per catalogue product.
- Money is counted when it moves: payments by `paidAt` (orders that have been paid, `hasBeenPaid`), less refunds by their `createdAt`. A store counts its own orders' totals and, on an order shared with other stores, only its lines (as its orders list does); refunds and returns on shared orders count only on the platform's dashboard. Order counts match the store's orders list (every order with its items).
- The numbers come from `lib/dashboard-stats.ts`, which loads the rows for the period and the one before it and adds them up as decimals per day (`toSalesTrend`); it takes the client so a script can run it in a transaction, and `lib/data/dashboard.data.ts` adds the access checks. Stock states (`lib/stock-states.ts`, `stockStatesSql`) are shared with the listings stock filter.

### Storefront
`apps/store` shows what `@workspace/commerce/visibility` allows, and nothing else. It uses the shared theme (`@workspace/ui/globals.css`) and the console's `ThemeToggle` in its header, with the old bs42.net's fonts: Arimo for text (`--font-sans`) and Rajdhani for every heading and title, in capitals (`--font-display`; `app/display-font.css` covers heading tags and shadcn's `font-heading`; product names and review titles keep their typed case with `normal-case`). Its favicon is Settings' `faviconUrl` only (there's no `app/favicon.ico`).
- **Header and footer** follow the old site: a thin top bar (`components/top-bar.tsx`: Settings' phone and email, and the site's own pages from `lib/site-links.ts`, which the phone menu lists instead), the logo row with the search centred, and the centred category bar in Rajdhani capitals. The footer opens with a thin brand-colour strip of promises (`components/promise-strip.tsx`, a carousel below `lg`), then a charcoal block in both themes (the `dark` class): "Need help? Call…" with Settings' phone, the Shop and Contact columns (Settings' contact details, General → Contact, `contactPhone` / `contactWhatsapp` / `contactEmail` / `contactAddress`, each only when set), and a centred copyright with Terms and Privacy once written. The footer has no margin of its own: each page's root ends with `pb-16`, and `main` is a full-width flex column so a page can fill down to the footer (the sign-in pages' grey band).
- **Offers**: customers see one offer per product, or per variant, never the stores. Across every store selling it, the offer is the one in stock, else the first due on an open purchase order, else the cheapest (`pickOffers` in `lib/product-cards.ts`). A card opens on its first offer, and picking a variant value on a card switches to that variant's offer.
- **Prices**: GHS at today's rate, with tax when it's on (`shelfPrice` in `@workspace/commerce/pricing`, rounded as an order rounds a line of one), the ex-tax price under it. Without a rate fresh enough to sell at (`getPricingContext`), no prices show. Stock lines come from `lib/stock-line.ts`: "Only N left" at the low-stock threshold, "Due w/c …" from the earliest `expectedOn` on an open purchase order (one already past says "On order").
- **Homepage**: a carousel of featured categories (the category form's Featured switch, `featuredCategories` in `lib/data/categories.ts`: those with something on sale, in menu order, at most 6), each slide the category's image (wide, about 1600×600) behind its name, description and "Shop now" (`components/home/category-carousel.tsx`, shadcn's `carousel` with `embla-carousel-autoplay`; it pauses on hover and focus and doesn't play for reduced motion). With no featured category it shows the store's name and description instead. Then "Shop by category" (`components/home/category-grid.tsx`: a card per top-level category with the same image cropped to 2:1, a tinted panel without one; one image serves both, so the form asks for the subject right of centre) and the featured products.
- **Listing pages** (`/c/[...slug]`, `/b/[slug]`, `/search`): `loadProductCards(scope)` loads every product in scope once, and `lib/catalogue-filters.ts` filters, counts, sorts and pages them in memory; every filter state is a URL, and filters are links (no JavaScript needed). Spec filters are the category's specs and those above it (`getFilterSpecs`), with values slugged into the URL (`?resolution=4mp`). A category's URL is its path of slugs; the last one finds it, and a stale path redirects. Categories with nothing on sale are left out of the menu and pages (`getCategoryTree`). Breadcrumbs put each `BreadcrumbSeparator` (an `<li>`) beside the items, never inside a `BreadcrumbItem`: nested list items are split apart by the browser's parser, and React's hydration then fails.
- **Caching**: the storefront has its own `unstable_cache` entries (settings, pricing, categories and their specs, product cards, brands, review summaries and pages), which expire after 60 s: the console's `updateTag` can't reach another app. The root layout sets `revalidate = 60` for the prerendered pages. Orders check stock and prices again. Per-customer and per-URL pages (the wish list, `/compare`) read cards uncached (`queryProductCards`).
- **Product page** (`/p/[slug]`, `?variant=` picks the variant; `?reviews=` / `?reviews-page=` sort and page its reviews): exists only while the product has an offer (`loadProductCards({ slug })`); `getProductDetails` adds the description, images, documents and each variant's SKU, barcode, weight and dimensions. Picking a variant (`useOfferPicker`, shared with the cards) updates the URL with `history.replaceState`, without a server round trip. Under the buttons, wide screens show the description's opening lines (`summaryLines` in `lib/data/product-details.ts`, each paragraph or line on its own, "Read more" to the tabs) and a help card (delivery, secure payment, Settings' phone and WhatsApp with the product named in the message, trade accounts). Product photos sit on white tiles in both themes (they're shot on white; grey only for a product without one), on cards, the product page, the basket, the wish list and compare.
- **SEO**: page metadata (canonical links, Open Graph) with `metadataBase` from `authURLs.store` (`STORE_AUTH_URL`, else https://bs42.net in production), `app/sitemap.ts` (every category, brand and product customers can reach; search is noindex) and `app/robots.ts`, and JSON-LD from `lib/structured-data.tsx` (`Product` with an `Offer`, or an `AggregateOffer` across variants, plus its `aggregateRating` and reviews; and `BreadcrumbList`). `JsonLd` escapes `<`, as Next's guide says.
- **Basket** (`lib/cart.ts`, actions in `lib/actions/cart.actions.ts`): a `Cart` keyed by the httpOnly `bs42_cart` cookie (`lib/cart-cookie.ts`), made on the first add. A signed-in customer's basket is their account's (`Cart.userId`), whatever the cookie says: `claimCart` (in `lib/cart.ts`, called by `readCartId`/`ensureCartId`) adopts the guest basket on sign-in, or merges it into the account's (quantities add up, to `MAX_LINE_QUANTITY`), and a signed-out visitor holding an account's basket cookie gets a new basket. One line per product or variant, held at one store's listing: adding picks a store already in the basket that has it in stock, else the offer the page showed, else the cheapest in stock (`chooseCandidate`). `loadCart` checks every line each time the basket is shown (moving it to another store, lowering it to the stock, or dropping it, with a notice) and prices it at today's rate. Out-of-stock offers can't be added (stock is reserved by the order, so no back orders), and a line holds at most `MAX_LINE_QUANTITY` (50, `lib/basket-limits.ts`). Baskets nobody has added to in `CART_LIFETIME_DAYS` (30, also the cookie's lifetime) are deleted by the console's unpaid-orders job. The header's count comes from `GET /api/basket` (pages are cached and shared) and the actions' replies (`components/basket/basket-count.ts`).
- **Checkout** (`/checkout`, `lib/checkout.ts`): delivery only, to towns with a fee; the customer's name and phone are the delivery's, and email is required (Paystack needs one). `priceCheckout` prices the basket with delivery to the chosen town (`quoteCheckoutAction` as the town changes, answering `BASKET_CHANGED` when `loadCart` changed the basket, so the page reloads; the form ignores a quote for a town no longer chosen); `placeOrder` refuses `TOO_MANY_UNPAID` past `MAX_UNPAID_ORDERS` (2) unpaid storefront orders per email or phone, or `MAX_UNPAID_ORDERS_PER_IP` (4) per `Order.placedFromIp` (the first `X-Forwarded-For` address, so the host's proxy must set it), since unpaid orders hold stock; `BASKET_CHANGED` when `loadCart` had to change the basket; and `PRICE_CHANGED` when the total isn't the one the page showed. Otherwise it creates the order (`createdById` null, unpaid, stock reserved) and empties the basket. Stock alerts go out then; the customer's confirmation and the staff's new-order email wait for the payment.
- **Online payments** (`@workspace/commerce/paystack` and `online-payments`, `PAYSTACK_SECRET_KEY`): each "Pay" is a `PaymentAttempt` with its own reference (Paystack takes a reference once), sent to Paystack's hosted checkout (mobile money and cards, GHS). A payment is recorded from whichever comes first: the customer's return (`/api/paystack/callback`, which asks Paystack), the signed webhook (`/api/paystack/webhook`, `charge.success`; set its URL in the Paystack dashboard), or the unpaid-order job. `recordPaystackTransaction` locks the order row and records each attempt once; it pays the order only for its exact total in GHS (card or mobile money, `paymentRecordedById` null), and reports a payment for a cancelled order (recorded on it, for a refund), a second payment, or a wrong amount as a problem, emailed to staff (`notifyPaymentProblem`). The order's status stays `PENDING` for staff to confirm; until it's paid its `paymentMethod` is `CARD`, a placeholder. Refunds given in the console are only recorded: the money goes back through Paystack's dashboard. The console's order pages list the attempts (`OrderPaymentAttemptsCard`, with each reference to search Paystack by; amounts hidden where a store sees only its lines; a checkout still open on a paid order shows "Not used", since nothing closes it).
- **Unpaid orders**: customers can start paying for `PAYMENT_WINDOW_MINUTES` (30); `POST /api/cron/unpaid-orders` in the console (a scheduler every 5 minutes, `CRON_SECRET`) cancels storefront orders still unpaid after `UNPAID_CANCEL_MINUTES` (45), with `changedById` null, putting their stock back, and emails the customer the order's link (`UNPAID_CANCELLED`, `OrderUnpaidCancelled`: not charged, put the items back in the basket). It asks Paystack about each open attempt first, and leaves an order Paystack can't answer for to the next run.
- **Order page** (`/orders/[reference]?key=`): for guests, the key is an HMAC of the order id with `BETTER_AUTH_SECRET` (`@workspace/commerce/order-links`, so the console's jobs can email the link too), so references can't be probed. Its Progress card (`lib/order-timeline.ts`, pure) lists what has happened (placed, paid, status changes but completed, refunds, returns with their refund) and the steps still to come; it shows only notes the customer's emails already carry, never the placing note. It offers "Pay" while the order can be paid, and "Put these items back in your basket" once it's cancelled unpaid.
- **Accounts** (`@workspace/auth/store`, `app/(auth)`, after shadcn's login-03/signup-03): `/sign-in`, `/sign-up`, `/forgot-password`, `/reset-password`, `/verify-email` (where sign-up's confirmation link lands, signed in; sign-in's `callbackURL` is also where Better Auth sends the browser once signed in, so sign-in passes the page to go back to, and a link it emails lands there) and `/orders/find`; `?redirect=` comes back afterwards, through `safeRedirect` (`lib/auth-redirect.ts`, site paths only). The header's `AccountButton` reads the session in the browser (pages are cached); for staff it adds "Open console" (`GET /api/account/console-access`, the console's `hasConsoleAccess` rule read from the database, as the store's session has no role or memberships), and the console's user menu has "View storefront" (its URL passed down from the `(root)` layout, since `STORE_AUTH_URL` doesn't reach client code). Email sign-ups confirm their address before they can sign in (`requireEmailVerification`; signing in unverified sends a new link), because guest orders will show in the account whose verified email matches; sign-up answers the same for an email that has an account, and emails that account instead (`onExistingUserSignUp`, `ExistingAccountEmail`). Sessions are shared with the console (the same `session_token` cookie), so the store's `session.create.before` hook refuses banned users, as the console's admin plugin does. The session cache cookie is not shared: the store's is `bs42-store.session_data`, since its cache holds only its own schema's fields (no `role`, no `activeOrganizationId`), which the console would read as a user with no role. Orders placed signed in get `Order.userId`. Customer auth emails go out in the store's name without being awaited (timing would tell existing accounts apart). Server code reads the session with `getStoreSession()` (`lib/session.ts`, once per request).
- **Account pages** (`app/account`, menu in `components/account/account-nav.tsx`, also the header's account menu): each page calls `requireCustomer(path)` (`lib/session.ts`), which sends a signed-out visitor to sign in and back. My orders (`/account/orders`, `lib/data/account-orders.ts`) lists orders with the account's `userId` plus, once the email is verified, any order whose `customerEmail` matches it (`accountOrdersWhere` in `@workspace/commerce/customer-orders`; nothing is copied onto the account), each linking to its order page with its key, with an Invoice button beside it (the card's main link is stretched over it, so the two don't nest). Reviews (`/account/reviews`): see Reviews. Wish list: see Wish list. Addresses (`/account/addresses`, `lib/addresses.ts`): up to `MAX_SAVED_ADDRESSES` (10), any GEODATA town; the first is the default, the default stays one until another is chosen, and removing it passes it to the newest. Checkout fills in the account's name, email and phone, and its default address when that town is delivered to, with a "Deliver to" picker (undeliverable towns disabled); a new address can be saved with the order (`saveAddress`, `rememberAddress` after the order commits, skipping duplicates and never failing the order). Email preferences (`/account/email-preferences`) saves `getOrderEmails` / `getMarketingEmails` per switch (`setEmailPreferenceAction`); order emails check only the order's linked account, so guest orders still email.
- **Find an order** (`/orders/find`, `findOrderAction`): emails the order's link (`OrderLinkEmail`) to the order's own address, after answering, and answers the same whether or not the order exists, so a reference and email never open an order by themselves. One email per order per 10 minutes (`Order.orderLinkSentAt`, claimed with an `updateMany`).
- **Reviews** (`Review`, `@workspace/commerce/reviews`): per product, never per store, one per customer per product (`@@unique([userId, productId])`). Only buyers: an order of the account's (`accountOrdersWhere`, so guest orders count once the email is verified) holding the product, delivered or completed, with not every unit returned; the review keeps that order line (`orderItemId`) and its `variantLabel` ("Bought: …"). Published at once; staff hide one with a reason its author sees (`status` HIDDEN, `hiddenReason` required by a CHECK), and editing a hidden review doesn't publish it. `Product.rating` (two places) and `numReviews` count published reviews only; every change (`saveReview`, `deleteReview`, `setReviewStatus`) locks the product row and recomputes them (`recomputeProductRating`). Staff moderate at `/catalogue/reviews` (system permission `product: update`; `?product=` from the product edit page's Reviews card and the alert email), with `setReviewStatus` taking the status the page showed (`STATUS_CHANGED`). On the storefront: stars on cards and the product page's header, a Reviews section under the tabs (`components/reviews/product-reviews.tsx`: average, a bar per rating, sorted and paged by links, `?reviews=` and `?reviews-page=`), a "Top rated" sort, `aggregateRating` and the first page's reviews in the JSON-LD, and Account → Reviews ("To review" from `productsToReview`, and the customer's own, hidden ones with the reason). Reviews are written at `/account/reviews/[productSlug]`, which the product page and the completed-order email link to. Plain text (title up to 100, body 20–2000); reviewers show as first name and last initial (`reviewerName`). A review that becomes 1 or 2 stars emails staff (`notifyLowRating`, the `notifyLowRatings` switch, off by default).
- **Wish list** (`WishListItem`, `lib/wish-list.ts`, `/account/wish-list`): signed-in customers only, per product or variant (never per store; a partial unique index for products without variants, like `CartItem`), up to `MAX_WISH_LIST_ITEMS` (100). Saving needs the item on sale (`ITEM_UNAVAILABLE`), so a product id can't reveal a hidden product; a saved item that stops being on sale stays, shown greyed with Remove (and "See other options" when only its variant is off sale). Hearts (`WishListHeart`) sit on cards and as "Save" beside the product page's "Add to basket"; pages are cached, so the saved state comes from `GET /api/wish-list` once per page (`components/wish-list/wish-list-state.ts`, refreshed on sign-out). A signed-out heart goes to sign in with `?save=<productId>[.<variantId>]` on the way back, which the header's `WishListButton` (on every page, hidden on phones) saves and strips. The page loads its cards with the uncached `queryProductCards({ productIds })` (the shared pages use the cached `loadProductCards`), at today's prices.
- **Compare** (`/compare?ids=`, `lib/compare.ts`, `components/compare/*`): whole products (not variants: spec values are per product), one category at a time, up to `MAX_COMPARE` (4). The picks live in this browser only (`compare-state.ts`, `localStorage` wrapped in try/catch, synced across tabs by the storage event), so guests compare too: a "Compare" checkbox on cards and the product page (`CompareToggle`; another category's product offers "Start a new comparison"), and `CompareBar` along the bottom of every page but `/compare` (a count only on phones). The page works from its URL alone (shareable, today's prices, noindex): cards from `queryProductCards({ productIds })`, products not on sale or from another category than the first left out with a note, rows from every spec of the category and those above it (`getCategorySpecs`, not only filterable ones), then condition, weight and dimensions (`compareRows`: rows nobody has are dropped, a missing value counts as a difference), with a "Show only differences" switch. A product with variants shows "From" its lowest price and "Choose options".
- **Trade accounts** (`TradeAccount`, one per customer account): a business applies at Account → Trade account (`/account/trade`, `lib/trade-account.ts`; company name, registration number, TIN as the GRA gives it or a Ghana Card number, phone, business type), which emails staff (`notifyTradeApplication`, the `notifyTradeApplications` switch, on by default); `/trade` explains it to anyone, linked from the footer. Staff review at `/trade-accounts` in the console (`lib/trade-account-reviews.ts`, `nextTradeStatuses`: Pending → Approved with a `discountPercent` or Rejected with a `rejectionReason` the customer sees and can re-apply after; Approved ↔ Suspended; the discount can change), each taking the status the page showed (`STATUS_CHANGED`); approval and rejection email the customer (`sendTradeDecisionEmail`, `TradeAccountDecisionEmail`). An approved account's terms (`loadTradeTerms`, `getTradeTerms` per request) make its checkout's discount a PERCENTAGE order discount (`tradeDiscount`, reason "Trade discount (10%)": goods only, before tax, and the free-delivery threshold counts after it), copy `tradeAccountId`, `tradeCompanyName` and `tradeTin` onto the order, and raise a basket line's limit to `TRADE_LINE_QUANTITY` (500). `placeOrder` loads the terms in its transaction, so a suspension since the page loaded gives `PRICE_CHANGED`. The basket and checkout show a trade account's amounts before tax, with the discount and tax as rows. Shelf prices come from cached pages, so `OfferPrice` asks `GET /api/trade` once per page (`components/trade/trade-state.ts`) and shows `tradeShelfPrice` (`lib/trade-price.ts`, rounded as `tradePrice` in `@workspace/commerce/pricing`). The console's orders show the company (`/orders` filters "Trade").
- **Invoices** (`/orders/[reference]/invoice?key=`, `invoiceHref`): every order's printable invoice behind the order page's key, linked from the order page and My orders, with the company and TIN for a trade order; the header, footer and compare bar are `print:hidden`. It's the only invoice: the console's order pages open it in a new tab (`InvoiceButton`, `invoiceUrl` signed on the server), a store's only for an order made of its own items, since the invoice shows the whole order.
- **Quotations** (`Quote` + `QuoteItem`; the shared rules in `@workspace/commerce/quotes`, the basket's side in the store's `lib/quotes.ts`, staff's in the console's `lib/staff-quotes.ts`): "Get a quote" under the basket's summary (signed-in customers; `QuoteRequestDialog` asks for the delivery address, filled in from the account) prices the basket exactly as checkout would (`priceCheckout`: rate, tax, trade discount, installation, delivery) and saves those amounts as the quote's, `QT-yyyyMMdd-00001` from `quote_reference_seq`; the basket stays. Its GHS prices hold for `AppSettings.quoteValidityDays` (7, Settings → Pricing) whole days in Accra time (`quoteValidUntil`: `validUntil` is the start of the day after the last); stock isn't held. "Expired" is an open quote past `validUntil`, worked out (`isExpired`, `openQuoteWhere`), never stored. At most `MAX_OPEN_QUOTES` (5) open per account (`TOO_MANY_QUOTES`; staff-made quotes don't count). A quote belongs to the account that made it or, once verified, the account with its email (`quoteOwnerWhere` / `isQuoteOwner`), so a staff-made quote is accepted by signing in (or up) with the address it was sent to. The page `/quotes/[reference]?key=` is printable like the invoice and signed like it (kind "quote", so an order's key never opens a quote), for forwarding to an approver; only the owner signed in sees "Accept and pay" and "Cancel". `acceptQuote` locks the quote row and checks the owner, `OPEN`/`EXPIRED` (`lockOpenQuote`), the unpaid-order limits (`checkUnpaidLimits`, shared with checkout), every line still on sale and in stock (naming every problem: `UNAVAILABLE`), then `createOrder` at the quote's stored amounts and rate (`placeQuotedOrder`), with the status note "Placed from quotation QT-…", and pays through `lib/payments.ts` like checkout (`paymentRedirect`). A lapsed or cancelled quote offers `quoteToBasketAction` (today's prices). It and a cancelled order's `reorderAction` top a line up to the quoted or ordered quantity (`AddToCartInput.atLeast`) rather than adding to it, since making a quote keeps the basket. Quote lines' links are `SetNull`, so a quote never stops a listing being deleted (the line becomes unavailable). The rate a quote used can't change (`RATE_IN_USE` counts quotes too). The customer is emailed the link (`sendQuoteEmail` in `@workspace/commerce/quote-emails`, `QuoteEmail`); staff optionally for a customer's own (`notifyNewQuote`, `notifyQuotes`, off by default). Account → Quotations lists them. The console's `/quotes` (system permission `order: read`) lists every quote (status, trade, made by customer or staff, made date), each with its page (`/quotes/[id]`), and an order from a quote links to it in its header.
  - **Staff-made quotes** (`/quotes/create`, system permission `order: create`): a wizard like the create-order one (customer → items → delivery and terms → review). The customer is looked up by exact email or phone (their saved addresses, and an approved trade account's discount as the starting discount and its company and TIN on the quote) or typed in; email and phone are required. Items come from what customers can buy (`searchQuotableItems`), each variant at the offer the storefront would sell (in stock, else on order, else the cheapest; staff see the store, customers never do), with installation per line where offered (`OUTSIDE_INSTALLATION_AREAS` outside the areas). Delivery is filled in from the fees and editable; one discount (fixed or percentage, with a reason); validity in days (Settings' default, at most 90); an optional note printed on the quote (`Quote.notes`). `Quote.createdById` records who made it ("Prepared by" on the quote and in the email). No drafts: saving emails it, and a sent quote isn't edited but cancelled and copied (`/quotes/create?from=`, today's prices). The quote's page cancels it (`order: update`) or places its order for a customer paying by bank transfer (`placeOrderFromQuote`: a staff-made order at the quoted prices, `PaymentMethod.BANK_TRANSFER`, unpaid, so the unpaid-order job leaves it and staff record the payment).
- **Terms and Privacy** (`/terms`, `/privacy`): written in the console's Settings → Legal (superAdmins, `LegalPages` singleton, rich text through `sanitizeRichText`, versioned by its `updatedAt`; each page's `*UpdatedAt` changes only when its text does and shows as "Last updated"). The store reads them with `getLegalPages()` (`lib/settings.ts`, cached like the rest). A page with no text 404s, and nothing links to it: the footer, the sitemap and `LegalConsent` (the "By creating an account / placing your order, you agree to our Terms and Privacy Policy" line under sign-up and checkout's Pay button) show only the pages that exist. No checkbox and no record of acceptance.
- It needs `apps/store/.env` with `DATABASE_URL` to build and run (and `AUTH_COOKIE_DOMAIN` for a production build, as the console), `BETTER_AUTH_SECRET` (order links) and `PAYSTACK_SECRET_KEY` to sell, and `SITE_MAILER_*` for account emails (without them nobody can confirm a sign-up).

### Staff notifications
Each notification is an email (the `StaffAlertEmail` template) and a row in the console's bell (`Notification`), both from `@workspace/commerce/notifications`; callers schedule them with `after()` once the change has committed, and they never throw. Whoever made the change isn't told about it.
- **The platform's** (`toPlatform`): emails to the addresses in Settings → Notifications (`AppSettings.notificationEmails`, not necessarily console users), by Settings' switch per event, and the bell of every platform admin (admins and superAdmins, not banned), by each admin's own switch at `/account/notifications` (`PlatformAlertSetting` per `PlatformAlert`; without a row, the alert's default, Settings' own; `setPlatformAlertAction`). `PLATFORM_ALERTS` in `@workspace/contracts` lists the alerts with their Settings key, default and words, for both pages. Callers pass their alerts and the content, or a function of which alerts the reader wants (stock lists only the kinds, low or out, each reader wants); payment problems have none, so always go out.
- **Store teams** (`toStoreTeam`): a store's owners and admins (not members, not banned users, and not platform staff, who belong to every store and get the platform's), each choosing per store at `/account/notifications` (`Member.notifyOrders`, `notifyStock` (also stock transfers), `notifyRefunds`, on by default, emails and bell alike; `setStoreNotificationAction`). New orders list only the store's lines (an order spanning stores tells each store its own); stock alerts carry `storeId`; refunds go to the store only on orders made entirely of its items.
- **Links** are console paths with `?workspace=<id>` (the store's, or the platform's), which `proxy.ts` turns into a switch to that workspace (Better Auth refuses one the user isn't in) before the page.
- **The bell** (`components/notification-bell.tsx`, in `AppHeader`) polls `GET /api/notifications` (`getBellNotifications`: the newest 20 and the unread count) every 15 seconds while the tab is visible, when it's shown again, and when opened. `/notifications` lists them all (`getNotificationsPage`, 25 a page, `?show=unread`, `?kind=`), with the same item (`components/notification-item.tsx`) and controls; the bell links to it ("View all"). A link into the session's own workspace loses its `?workspace=` and opens as a client navigation; one into another workspace is a full page load, so the sidebar follows the switch. Opening one marks it read (`markNotificationReadAction`; also "Mark all as read"); read ones stay listed until dismissed (the × on each, `dismissNotificationAction`, or "Clear read", `clearReadNotificationsAction`). The unpaid-orders job deletes notifications older than `NOTIFICATION_LIFETIME_DAYS` (90).
- New orders: `notifyNewOrder(orderId, "storefront" | "store" | "platform")`. `createStoreOrderAction` sends "store", the platform's `createOrderAction` and `placeOrderFromQuoteAction` send "platform" (both under the `STAFF_ORDERS` alert); a storefront order sends "storefront" once it's paid (`sendPaymentEmails`).
- Payment problems (`notifyPaymentProblem`, no switch): a payment for a cancelled order, a second payment, or the wrong amount.
- Product requests (`notifyProductRequest`, `notifyProductRequestDecision`) and stock transfers (`notifyStockTransfer`): see their sections.
- Stock: `createOrder` returns `stockAlerts` for the items a sale took to their low-stock threshold (crossing it, so no repeats while it stays low) or to 0, which `notifyStockAlerts` sends as one email. Stock edits by staff don't alert.
- The exchange-rate cron route calls `notifyRateFetchFailed` when the fetch fails.
- Low ratings: `notifyLowRating(reviewId)` when a customer's review becomes 1 or 2 stars (`notifyLowRatings`, off by default).
- Refunds (on their own, with a cancellation or with a return) call `notifyRefund(orderId, storeId, …)`: the platform hears of a store's own (`storeId`), not of its own superAdmins'; the store's team hears of either on its own orders.
- Trade account applications: `notifyTradeApplication(accountId)` (`notifyTradeApplications`, on by default).
- Quotations: `notifyNewQuote(quoteId)` (`notifyQuotes`, off by default).

### Console app conventions
- Routes are grouped: `(auth)` pages are public, `(root)` is the authenticated shell, and `(misc)` holds `no-stores` and `accept-invitation`. Route-specific components live in `_components/` next to the page.
- Server actions live in `lib/actions/*.actions.ts` (`"use server"`), validate input with zod schemas from `lib/schemas/*.schemas.ts`, and return `ActionResponse` from `@workspace/contracts`. Data loaders live in `lib/data/`.
  - Every exported action is a public endpoint, so each one calls its guard (e.g. `requireSystemPermission`) before its `try` block: `redirect()` works by throwing, and a `catch` would swallow it.
  - Report conflicts with a `code` the form can match (`EMAIL_EXISTS`, `NAME_EXISTS`), not the `formatError` text. Under the pg driver adapter Prisma leaves `meta.target` empty; the constraint name is in `meta.driverAdapterError.cause.constraint.index`, which `formatPrismaError` uses to name the field.
  - Loaders for `SelectField` options return `SelectItem[]` (`{ id, name }`, from `@/types`).
- Zod schemas: use `z.httpUrl()` for URLs, since `z.url()` accepts `javascript:`. When a schema has transforms, type the form as `useForm<z.input<S>, unknown, z.output<S>>` and its submit handler with `z.output<S>`.
- Images on edit forms: the action rejects URLs outside our container (`isManagedFileUrl`) and removes the replaced image only after the update succeeds (brands, app settings). The form must not delete the saved image when it's removed, only images uploaded during that edit. Stores update through Better Auth, so a replaced store logo is left to the orphaned-file sweep.
- Toasts: `toast` from `@workspace/ui/components/toast` is Base UI's toast manager. Use `toast.add({ title, description, type })`; there is no `toast.success`/`toast.error`.
- A dialog with a form that saves through an action (refunds, returns, receiving, cancelling a purchase order) is a `FormDialog` (`components/form-dialog.tsx`), with the codes that mean "changed under the page" in `refreshOn`. An add button in the store workspace is a `StoreAddButton`.
- Action buttons (e.g. `DeleteStore`, `DeleteBrand`) check their own permission from the client session (store permissions via `useMemberRole` and `checkRolePermission`), show a skeleton while it loads and a line explaining a disabled button. The server action checks again. Pages don't pass `canX` props; a table fetches the role once and hands it to its cells. Page guards stay on the server.
- An action that changes something another person might have changed takes the value the page showed (`currentStatus`, `currentRole`, `original`) and refuses with a code (`STATUS_CHANGED`, `ROLE_CHANGED`, `NOT_PENDING`, `CONFLICT`) instead of overwriting; the UI refreshes on those codes.
- Transaction logic worth testing lives in its own `server-only` module with relative imports (`lib/product-sync.ts`, `lib/product-specs.ts`, `lib/listing-sync.ts`, `lib/order-refunds.ts`, `lib/purchase-order-writes.ts`, `lib/stock-transfer-writes.ts`, `lib/staff-quotes.ts`, `lib/staff-orders.ts`, and `packages/commerce`'s `order-writes.ts`, `stock-movements.ts` and `reviews.ts`; in the store, `lib/cart.ts` and `lib/wish-list.ts`), so a script can run it against the database. Don't use TypeScript parameter properties there: Node's type stripping rejects them.
- Uploads go through `app/api/storage/{images,documents,files}/route.ts` → `lib/storage-api.ts` (per-route `UploadPolicy`) → `@workspace/storage` (Azure Blob via `DefaultAzureCredential`; `AZURE_STORAGE_ACCOUNT_NAME`, optional `AZURE_STORAGE_CONTAINER_NAME`). `/api` skips `proxy.ts`, so these routes check for a console user themselves, and the delete route refuses files a record still references (`findReferencedFileUrls`): the browser only deletes unsaved uploads. Images are JPEG, PNG, WebP or GIF (no SVG, which can carry script), and every upload, PDFs too, must begin with its declared type's signature (`FILE_SIGNATURES` in `lib/storage-api.ts`), since the declared type is the uploader's word and the blob is served with it; `ImageField` offers the same four types by default, and shows each image whole in a square tile with only its remove button: blobs have generated names, so there's no filename worth showing.
- Invitations last 7 days (`INVITATION_EXPIRATION_SECONDS`). `/accept-invitation` is a public path in `proxy.ts`: the page sends a signed-out invitee to sign-up or login, offers "Sign out and continue" to someone signed in as another account, and explains an invalid invitation instead of redirecting.
- Store input is checked in the organization hooks (`packages/auth/src/store-input.ts`), because store admins can call Better Auth's organization endpoints directly: logos must be our own blobs, and only system admins may change a store's status.
- Rich text (`RichTextField`) is stored as TipTap JSON, not HTML; an empty editor is `null`. Actions save it through `sanitizeRichText` (`@workspace/utils/rich-text`), which keeps only the nodes, marks and attributes the editor can produce and links with http(s)/mailto/tel. Render it with `RichTextContent` (`@workspace/forms/components/rich-text-content`, TipTap's static renderer with the editor's own `richTextExtensions`; works in server components), never as raw HTML. A new editor extension goes in `richTextExtensions` and `sanitizeRichText` both.
- Form fields come from `@workspace/forms` (react-hook-form wrappers; `CascaderField` wraps the controlled `Cascader` in `@workspace/ui`, which table filters use too), data tables from `@workspace/tables` (TanStack Table), and primitives from `@workspace/ui`. `NumberInputField` rounds to its `step` when it loses focus, so the step must match the value's stored precision (the exchange rate uses 0.000001), or clicking in and out changes the value and marks the form dirty. `TextInputField` and `TextareaField` show a "12 / 100" count under the field with `showCount` and `maxLength` (`FieldHint`); give a field with a length limit in its schema the same `maxLength`.
- Descriptions (page subtitles, cards, fields, dialogs) are one short sentence: what it is, or the one consequence someone must see before acting ("can't be undone"). How it works goes behind an ⓘ: `InfoTip` (`@workspace/ui/components/info-tip`, a popover that opens on hover, tap or the keyboard), through the `info` prop on the `@workspace/forms` fields (beside the label, via `FieldLabelWithInfo`), `SettingsCard` and `FormDialog`, or inside a `CardTitle` with `className="flex items-center gap-1.5"`. Never put a warning only in an `InfoTip`.
- Form fields take their element ids from `useId`, so two forms on one page (a dialog over a form) never share an id. A page form's layout follows the product and listing forms: a `FieldGroup` per card, side-by-side pairs in `grid gap-5 sm:grid-cols-2`, and the cards and `SharedFormFooter` inside `grid gap-8`.
- Table rows link to their page with `DataTable`'s `getRowHref`, which makes the main cell a real link. A cell that needs a second link (links can't nest) sets the column's `meta: { rendersRowLink: true }` and renders `RowLink` itself; clicks on any link in a row keep their own target, and the row-selection checkbox must stop its click (`onClick={(e) => e.stopPropagation()}`) or ticking it opens the row. `DataTableTree` shows nested rows (`getSubRows`, same `getRowHref`) and isn't paginated. `selectionActions(rows, clear)` shows a bar with what can be done to the ticked rows of the current page (`clear` unticks them once an action has dealt with them); pass `getRowId` with it, so a selection stays with its rows, not their positions, when the page changes. The filters toolbar (`FiltersToolbar`) is one row, after shadcn's data table: `text` filters are search boxes that apply as you type (after a pause, replacing the history entry), and `select`, `boolean` and `tree` filters are dashed buttons with a searchable list (`filters/faceted-filter.tsx`; a select's `"all"` option is dropped, "Clear filter" does its job), so give every filter a short `label`: it's the button's text. Toolbar filter types: `text`, `select`, `tree` (nested `tree` options in a `Cascader`, any level choosable), `number`, `boolean` (`true`/`false`), `date` (a plain `yyyy-MM-dd` day), `dateRange` (two plain days, `<key>Start` and `<key>End`, both included; read them with `getDayParam` and filter from `dayStart(start)` to before `dayStart(end, 1)`), `numberRange`.
- An empty list, table or card shows `EmptyState` (`@workspace/ui/components/empty-state`, on shadcn's `empty`; the storefront's empty pages use it too): an icon, a short title ("No suppliers yet") and one line saying what would be there or what to do. Give every `DataTable` / `DataTableTree` an `empty` (`{ icon, title, description }`); when filters hid every row it shows "No results" with "Clear filters" itself. Searches in pickers and wizards show "No matches"; a field with nothing set ("None attached.") stays a line of muted text.
- A form that checks a step with `trigger()` (the create wizards) or fills fields in code (`setValue`: a looked-up customer, a saved address) calls `useRevalidateOnChange(form)` (`@workspace/forms/use-revalidate-on-change`), so a fixed field loses its error as it changes; react-hook-form re-checks only typed changes, and only after a submit. `FormDialog` already does.
- Shared table cells live in `components/` so tables show the same thing the same way (e.g. `CategoryPath`, which mutes the parent categories).
- A link from a store's workspace to a global page (the catalogue) is a `GlobalWorkspaceLink`: route access ties each page to a workspace, so it switches the session to the platform org first (`useStoreSwitcher` with a `to` page; the switch applies to every tab of the session). It renders plain text, or nothing with `hideWithoutAccess`, for users who aren't system admins.
- A server component that imports a value (not a type) from a `"use client"` module gets a client reference, not the value. Constants both sides use go in a plain module (e.g. `app/(root)/_components/periods.ts`).
- Prefer Prisma's query API over raw SQL, for readability. Raw SQL is only for what Prisma can't express (row locks, sequences, comparisons across tables, "more than one store"), with a comment saying why; it's always the tagged `Prisma.sql` / `$queryRaw` template, never `$queryRawUnsafe` with values.
- Dates rendered in client components use `formatDate` from `@workspace/utils/date`. It formats in one fixed zone so the server render and hydration match.
- A form inside a dialog must call `e.stopPropagation()` before `handleSubmit`. React bubbles events through portals, so otherwise submitting the dialog also submits the page form around it.
- Never include `Session` rows in data passed to client components: each row holds its token.
- A page's root is a `div`: the shell's `SidebarInset` is the page's `<main>`, and a page has one. Pages outside the shell (`/setup`, `/forbidden`) keep their own.
- Phones are stored international (`+233244123456`); show them with `formatPhoneNumber` (`@workspace/utils/phone`, "+233 24 412 3456"), keeping the raw number in `tel:` links.

### UI components
Add shadcn components from the repo root with `pnpm dlx shadcn@latest add <component> -c apps/console`. They land in `packages/ui/src/components` and are imported as `@workspace/ui/components/<name>`.

The primitives are built on Base UI, not Radix. Use `render={<Button />}` instead of `asChild`, and give menu items `onClick`: `onSelect` type-checks but never fires. A menu item that navigates is a `DropdownMenuLinkItem` (Base UI's `Menu.LinkItem`, a real `<a>`) with `render={<Link href="..." />}`.

- The style is `base-vega`. Blocks previewed on shadcn's site are usually the Radix (`new-york-v4`) versions, whose defaults differ: Radix's `ToggleGroup` takes `type="single"` and joins its items (`spacing` 0), Base UI's selects one by default (`multiple={false}`) and spaces them apart (`spacing` 2), so pass `spacing={0}` for the joined look. Fetch a block's `base-vega` source from `https://ui.shadcn.com/r/styles/base-vega/<name>.json`, and check its container-query breakpoints (`@[767px]/card`) against the column the block is put in.
- `shadcn add` skips files that already exist (it did for `toggle.tsx` and `card.tsx`); compare those with the registry's current version when a new component depends on them.
- A searchable list of items to add (the order and quote wizards' item steps, purchase orders, stock transfers) scrolls in shadcn's `ScrollArea` (`flex max-h-[60vh] flex-col`, so a short list keeps its own height), not the browser's scrollbar or a page that grows.
- Charts use shadcn's `chart` (Recharts 3.8.0). A chart component imports Recharts' parts itself, so `recharts` is a dependency of the console as well as `packages/ui`.

### Email
`@workspace/email` holds React Email templates (auth flows, including the storefront's `VerifyEmailEmail` and `ExistingAccountEmail`; member invites; order lifecycle under `templates/order/`, including `OrderUnpaidCancelled` and `OrderInstallationBooked`, plus `OrderLinkEmail` for finding an order, `TradeAccountDecisionEmail` for trade accounts, `QuoteEmail` for quotations and `OrderReviewRequest` for reviews; and `StaffAlertEmail` for staff notifications) sent via Nodemailer (`SITE_MAILER_*` env vars). The sender name and logo come from app settings: the console's name for staff emails, the storefront's (`resolveStoreName`) for customer emails, including the store's account emails. Their header is dark, so they take the logo for dark backgrounds (`resolveDarkLogoUrl`: Settings' `logoDarkUrl`, else `logoUrl`), which the sites also show in dark mode. The header's colour is also drawn as a one-colour gradient (`DARK_FILL`, `templates/dark-fill.ts`): Gmail's apps recolour backgrounds and text in dark mode but not images, so this keeps the header dark under the white logo. Never on buttons or text, whose text Gmail would still darken. `@workspace/commerce` and the store import it for order emails and staff notifications, so build its `dist/` before the console.

## Environment

Required: `DATABASE_URL` and `BETTER_AUTH_SECRET` (≥32 chars, the same in both apps: they share session cookies, and the store signs order links with it, so changing it breaks links already sent). Optional, with defaults: `CONSOLE_AUTH_URL` and `STORE_AUTH_URL` (localhost:3000 / :3001 in dev; a production build defaults to the bs42.net addresses, so set both in both apps' `.env` for a local production build, or Paystack's return URL, the sitemap and the apps' links to each other point at bs42.net). Required in production: `AUTH_COOKIE_DOMAIN` in both apps (`localhost` works for a local production build). Optional: the Google OAuth credentials (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, the store's "Continue with Google"; its redirect URI is `<store>/api/auth/callback/google`). For features: `SITE_MAILER_*` (email), `AZURE_STORAGE_ACCOUNT_NAME` / `AZURE_STORAGE_CONTAINER_NAME` (uploads), `CRON_SECRET` (the `/api/cron/*` routes), `OPEN_EXCHANGE_RATES_API_KEY` (the daily rate fetch) and `PAYSTACK_SECRET_KEY` (storefront payments, and the console's unpaid-order job). Env vars must also be listed in `turbo.json` (`globalEnv` / `globalPassThroughEnv`) to reach tasks. `docs/launch-checklist.md` is the production setup (env vars per app, storage, Paystack, cron jobs, first-run steps): update it with any new env var, scheduled job or required setting.

Both apps send security headers from their `next.config.ts` (no framing by other sites, `nosniff`, `strict-origin-when-cross-origin`, HSTS, no `X-Powered-By`). Embedding a page elsewhere, or a third-party script or frame, means revisiting them.

## Style

Prettier: no semicolons, double quotes, `printWidth: 200`, Tailwind class sorting (`cn`, `cva`). Apps import their own code via the `@/` alias.

The shadcn components in `packages/ui/src/components` keep shadcn's own formatting, and so do most fields in `packages/forms/src/components` (80 columns; a few use long lines). Don't run prettier on one you edit: it rewrites the whole file. Match its existing style by hand.
